Implementation of SecureSDP · IJIS 2024

SecureSDP

A Software-Defined Perimeter in Go that scales across organizations. Each domain keeps its own controller, a root controller decides for all of them, and accepting hosts stay dark until a client presents keys issued for that grant alone.

Architecture

Three modules, as in the paper

One Go module and three binaries, named after the paper. Identities are X.509 certificates; every channel uses mutual TLS.

{% include ".icons/material/laptop.svg" %}

Initiating host

Authenticates to the controller of its domain, requests a service, sends the SPA packet and connects, directly or through an mTLS tunnel.

sdp-client
{% include ".icons/material/source-branch.svg" %}

Controller

root is the policy decision point, SPA key issuer and Egida master. bridge fronts a domain and relays to the root.

sdp-controller
{% include ".icons/material/wall-fire.svg" %}

Accepting host

Policy enforcement point: default-deny iptables, fwknopd with one stanza per grant, mTLS tunnel, hardening and audit agent.

sdp-services
{% include ".icons/material/certificate-outline.svg" %}

Bridge-CA PKI

A root CA and one name-constrained CA per domain, so a bridged domain can only vouch for its own members.

sdp-controller pki
{% include ".icons/material/shield-check-outline.svg" %}

Dynamic hardening

The root derives an Egida (Aspida) program per accepting host from the services it exposes, and collects Lynis audits.

hardening · audit

Quick start

A two-domain lab in two commands

The Compose lab runs a root and a bridged controller, a gateway in front of nginx, an authorized and an unauthorized client. The PKI is generated at start-up; CI runs the same demo on every change.
