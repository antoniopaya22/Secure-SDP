Bridge-model Software-Defined Perimeter

Many domains.
One decision.

Each domain keeps its own controller; a root controller decides for all of them over mutual TLS. Services stay dark until a client presents keys issued for that grant alone.

The problem

One controller
does not scale.

Classic SDPs put every member behind a single controller. Growing organizations either funnel everything through it or rebuild their topology, and the SDP components themselves stay as exposed as any other host.

A single bottleneck

Every authentication and authorization goes through one place.

Topologies get rebuilt

Merging existing perimeters means redesigning them around one controller.

Components stay soft

Controllers and gateways rarely get hardening tailored to their role.

Hierarchical

Tree of SDPs with clear delegation. Moderate redundancy.

Medium complexity

Web

Redundant pathways without a strict hierarchy.

High complexity

Mesh

Every node connects to every node. Very resilient, costly to run.

Very high complexity

Bridge CA

Bridges existing SDPs and keeps their topology. Chosen by SecureSDP.

High complexity · best for large deployments

How it works

Decide once,
at the root.

Bridged controllers authenticate their own members and relay requests over a persistent mutual-TLS peer link. The root re-verifies every client chain, applies the policy and installs a dedicated SPA stanza on the accepting host.

01

Authenticate locally

Each domain CA is name-constrained to its domain, so it can only vouch for its own members.

02

Relay with proof

The bridge forwards the request and the client chain; the root does not trust the bridge blindly.

03

Issue and enforce

Fresh Rijndael and HMAC keys per grant; revocation closes tunnels and removes rules.

Run it

Policy in,
perimeter out.

The root controller holds one policy for every domain. The Compose lab starts a root and a bridged controller, a gateway in front of nginx and two clients, with the PKI generated at start-up.

lab/config/policy.yml
services:
  - name: web
    gateway: gw-a
    target: 10.232.1.30:80
    mode: tunnel                 # mTLS tunnel to nginx
    hardening: [http-service]

clients:
  - id: alice
    domain: domain-b
    services: [web, web-nat]
  - id: bob                      # registered, no entitlements
    domain: domain-b
    services: []
terminal
$ docker compose up -d --build --wait
$ docker compose exec ih-alice sdp-client access web-nat --wait

Results reported in the paper

Scales out,
hardens in.

The paper compared HTTP response times of Bridge, Mesh and Hybrid topologies three layers deep: Bridge was consistently fastest, with Mesh close behind at a higher cost. It also audited the controller before and after applying Egida controls.

Questions.

Is this the code used in the paper's evaluation?

No. When the paper was published the repository held only a skeleton and an OpenSPA test bed. This implementation was written in 2026 following the architecture the paper describes; the paper's numbers were not regenerated with it. See history and provenance.

What does the Bridge model add?

Existing SDPs keep their own controller and members. A root controller decides for all of them through bridged controllers, so perimeters can be joined without rebuilding them.

Does it apply Egida hardening?

The root derives an Aspida program per accepting host and pushes it over the control channel. The lab uses a dry-run driver; on a Debian host with Egida installed the egida driver applies it. Lynis audits are reported back to the controller.

Can I run it in production?

It is research software. Review the policy, the PKI handling and the hardening profiles before using it outside a lab. Two controller levels are supported (root and bridges).

How does it relate to SDP Lab?

Both accompany the same article. SDP Lab runs the Waverley Labs SDP with fwknop; SecureSDP is the Go implementation of the Bridge model.

How do I cite it?

Cite the SecureSDP article in the International Journal of Information Security 23(4), 2793–2808, 2024. BibTeX is on the paper page.
